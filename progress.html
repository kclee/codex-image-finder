OCR trial results

Review annotated results

  • 40 representative images processed: the deterministic sample spans major folders and includes uncommon formats and orientations.
  • 37 images had some detected text; 33 had Chinese characters; 26 had likely lower-frame Chinese subtitles.
  • 13 images needed a second pass over the lower portion of the frame.
  • Zero processing errors were recorded in the final trial.
  • Runtime: 769.8 seconds total, averaging 19.2 seconds per image on CPU. A full CPU scan at that rate would take roughly 18 hours, so acceleration or a faster first-pass strategy is needed before scaling.

Early quality observations

  • Clean outlined subtitles can be recognized extremely well. Spot checks included exact readings such as 好想吃冰淇淋哦 and 妳應該選一句 / 妳餘生都會用的話來試筆.
  • The engine can read both Traditional and Simplified Chinese in the trial.
  • Colorful television graphics and parts of faces can create false text detections.
  • “Chinese characters found” is not the same as “subtitle correctly read”; human review is needed to establish real accuracy.
  • Tall, text-heavy reference images take much longer than ordinary drama frames and should follow a different processing path.

User review of OCR trial

Overall conclusion: generally good. OCR on the main target—drama screenshots with Chinese subtitles—worked well enough to continue. Lower-quality handling of decorated text in drawings, games, stickers, and other non-drama images is not currently a concern.

  • Good samples: 2, 7, 8, 10, and 24.
  • Bad samples: 13, 16, 17, and 18.
  • Bad sample 13 has no visible Chinese subtitle and includes false detections on a hand and smiley.
  • Bad samples 16 and 17 are small decorated stickers.
  • Bad sample 18 is an English Tamagotchi chart.
  • Sample 10 demonstrates that a result can remain useful for search despite a one-character OCR mistake.

Decision: optimize and evaluate around drama subtitles first. Retain other images in the library, but treat their text-recognition quality as secondary.

OCR speed benchmark

Open benchmark report

Five user-approved drama screenshots were processed with four configurations. Model initialization and downloads were excluded from inference timing.

  • Server / full frame: 12.22 seconds per image; baseline text retained.
  • Server / lower 55%: 8.36 seconds; 98.33% text similarity.
  • Mobile / full frame: 0.96 seconds; 100% text similarity.
  • Mobile / lower 55%: 0.72 seconds; 100% text similarity.

Decision: use the PP-OCRv5 mobile model on the lower 55% as the first pass, then use broader or server OCR only when the first pass is empty or uncertain. This controlled sample was 17.06× faster than the original baseline with identical approved subtitle text.

Selected Python application architecture

  • Python: one language for scanning, OCR, indexing, search logic, and application behavior.
  • PaddleOCR: retain the validated PP-OCRv5 mobile-first subtitle pipeline.
  • Pillow and OpenCV: image metadata, subtitle cropping, preprocessing, and thumbnails.
  • SQLite with FTS5: persistent image metadata, OCR text, user labels, and full-text search.
  • PySide6 / Qt desktop UI: one native application window containing the search box, filters, thumbnail gallery, preview, corrections, and file actions.

Scope decision: there will be no browser and no FastAPI layer in the initial product. C# and F# remain deferred.

Standalone application requirement

The user wants a Picasa-style experience: launch one installed program from one shortcut, work in one window, and never manage a browser or server.

  • Single window: PySide6 owns the entire interface.
  • Same process: SQLite, folder browsing, search, thumbnails, and normal application logic run directly in Python.
  • Background work: OCR and indexing run through Qt background workers so the gallery remains responsive.
  • Distribution: use a portable application folder with one executable and an optional desktop shortcut; no traditional installer is required.
  • Development launcher: provide a command/shortcut that starts the project-local Python environment with pythonw.exe, avoiding a persistent console window.
  • Finished launcher: package a portable one-folder build containing ImageFinder.exe, Python/Qt libraries, and OCR models.
  • Packaging preference: avoid forcing large OCR models into a self-extracting single file. The portable folder is technically several internal files but behaves as one click-to-run app.
  • Cross-PC use: the complete portable folder can be zipped, copied to another compatible Windows PC, unzipped, and launched without installing Python.
  • Portable data: keep settings, database, thumbnails, and model files relative to the application folder rather than under a specific Windows user profile.
  • Library selection: prompt for the screenshot folder on first launch and allow its location to be changed, instead of hard-coding C:\Users\kckck\Desktop\Output.
  • Path resilience: store image paths relative to the chosen library root where possible so a copied image library can be relinked on another computer.

What we are solving

  • Years of screenshots spread across folders and subfolders.
  • Frames often contain Japanese-drama actors and Chinese subtitles.
  • Useful or funny images are difficult to rediscover manually.
  • Other sources may include animation and US dramas.

Desired searches

  • Exact, partial, or imperfect subtitle text.
  • Traditional and Simplified Chinese equivalents.
  • Meaning or topic, even when wording differs.
  • Mood, scene, person, show, folder, or approximate date.
  • Combinations such as “sarcastic + restaurant.”

Small-step roadmap

  1. Read-only inventory. Count image types, folders, dimensions, naming patterns, and likely duplicates.
  2. Representative OCR trial. Test 30–50 varied screenshots before scanning the full archive.
  3. Basic text index. Store paths and recognized subtitles in a rebuildable local SQLite database.
  4. Gallery UI. Add search, filters, thumbnails, preview, correction, copy, and open-original actions.
  5. Meaning and mood. Add multilingual semantic and visual search after the basic search works well.
  6. Optional enrichment. Consider face grouping, show labels, near-duplicates, collections, and automatic rescanning.

Current technical direction

  • Local-first processing.
  • PaddleOCR as the first Chinese/Japanese OCR candidate.
  • Preserve raw OCR and add normalized search forms.
  • SQLite full-text search for the first index.
  • Semantic image/text models only after OCR evaluation.

Operating rules

  • Never move, rename, or alter original screenshots.
  • Test a small sample before expensive full-library work.
  • Make generated data safe to delete and rebuild.
  • Keep changes incremental and document each milestone here.
